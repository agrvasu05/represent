# RePresent

**A recovery agent for failed UPI Autopay / e-mandate debits that never
breaks the rules it operates under — and proves it with an independent
compliance auditor.**

In August 2025, NPCI capped mandate re-presentations at **1 attempt + 3
retries**, confined executions to **non-peak windows**, and RBI's e-mandate
framework requires a **24-hour pre-debit notification**. Most retry
automation is now non-compliant by design. RePresent treats those rules as
hard constraints and recovers the money anyway: it classifies why a debit
failed, schedules salary-aware compliant retries, falls back to payment
links with opt-out-respecting nudges, holds fire during bank outages, files
RBI TAT compensation claims when banks sit on reversals, and stops when the
rules say stop.

## Results (5,000 mandates/seed × 5 seeds, held-out split, mean ± sd)

| Policy | Recovery (by value) | Recovery (by count) | Compliance violations | Retries per recovery | Nudges to unrecoverable customers |
|---|---|---|---|---|---|
| No retry | 0% | 0% | 0 | — | 0 |
| Naive retry bot | 37.7% ± 2.4 | 42.1% ± 1.5 | **12,309** | 7.13 | 976 |
| **RePresent** | **39.8% ± 1.9** | **45.0% ± 0.8** | **0** | **2.80** | **400** |
| Oracle (upper bound) | 43.8% | 49.4% ± 1.1 | 0 | 1.90 | 0 |

- The naive bot's 12,309 violations per seed are the realistic ones: peak-window
  executions, missing pre-debit notifications, and messages to customers who
  revoked consent. Zero for RePresent is a **property, not luck** — see
  `tests/test_compliance.py::test_revoked_never_contactable`.
- **Bank-outage failure case:** during a seeded 5-day bank degradation the naive
  bot burns **174** retries into a dead bank and recovers **53.2%** of the
  affected cohort; RePresent's telemetry circuit breaker holds retries (9 burned)
  and recovers **70.4%**. The oracle, which knows the outage calendar, burns 0.
- **TAT module (RBI DPSS 629):** ~53 late/absent reversals detected per seed,
  ₹40,800 of ₹100/day compensation identified for customers, **claim precision
  1.0** (every claim independently recomputed by the auditor against ground
  truth). Reported separately from merchant revenue — the beneficiary is the
  customer.
- **Classifier (held-out):** 93.2% accuracy; 6.6% of narrations gated below the
  confidence threshold and routed to a human instead of guessed. ~30% of events
  have no clean error code — that messy-text slice is the LLM's job.

Every number above is generated by `make eval` (out/metrics.md); nothing is
hand-typed. Numbers move slightly if you change the seeds — that's the point.

```bash

make test        # compliance property tests
make demo-live   # one decision executed on real Razorpay TEST rails
                 #   needs RZP_KEY_ID=rzp_test_... RZP_KEY_SECRET=...

                 #   needs ANTHROPIC_API_KEY; cache is committed, so
```

chart with outage windows shaded), `out/audit_trail_sample.jsonl`.

## Architecture

```
                     ┌────────────────────────────────────────────┐
   failed debit ────►│ classifier: code map ► Claude (messy text) │
   (code+narration)  │   confidence < 0.70 ► UNKNOWN ► human      │
                     └────────────────┬───────────────────────────┘
                                      ▼
   bank telemetry ──► circuit ┌──────────────────┐   ┌──────────────┐
   (decline counts)   breaker │  POLICY ENGINE   │──►│ audit trail  │
                              │  deterministic:  │   │ (append-only │
   train-split lift ─────────►│  cause ► plan    │   │  JSONL)      │
                              │  constraints:    │   └──────┬───────┘
                              │  1+3, non-peak,  │          ▼
                              │  24h PDN, masks, │   ┌──────────────┐
                              │  stop rules      │   │ INDEPENDENT  │
                              └───────┬──────────┘   │ AUDITOR      │
                                      ▼              │ (no imports  │
                     ┌────────────────────────────┐  │  from agent) │
                     │ executor: simulator | REAL │  │ R1..R5 ► 0   │
                     │ Razorpay test-mode APIs    │  └──────────────┘
                     └────────────────────────────┘
```

- **LLM at the edges, determinism at the core.** Claude classifies messy
  Hinglish bank narrations and drafts nudges (behind a hard rubric gate);
  the scheduler, constraints, and arithmetic are exact code. Why: see
  [DECISIONS.md](DECISIONS.md) #2 — auditability is the product.
- **The auditor is a separate package** that never imports from `agent/`.
  It re-derives every rule from the log plus ground truth. The policy's
  own constraint checks are claims; the auditor's count is the metric.
- **Plans, not queues.** Retries are planned internally and dispatched
  day-by-day, which is what lets the circuit breaker hold a planned retry
  against a bank whose decline telemetry says it's down — burning budget
  into an outage is how naive bots permanently lose customers.

## Data honesty

Razorpay test mode cannot simulate failed mandate debits (mandate auth is
mocked; debits only work within 3 days of token creation). A calibrated
simulator is therefore the honest instrument, and the claims are
**relative** — policy vs baselines in identical worlds:

- **Common random numbers:** outcomes are drawn from
  `hash(seed, mandate, action, time)`. Same action, same world, same luck.
- **Calibration is labeled:** every constant in `simlab/generator.py` is
  `[CITED]` (NACH return-code mix, NPCI decline rates, salary-day
  clustering, RBI/NPCI rule parameters) or `[ASSUMED]` (exercised by
  sensitivity runs).
- **Train/held-out split (60/40 by id-hash):** the one learned quantity —
  the salary-window timing lift — is estimated on train by a probe policy
  and only ever applied on held-out.
- **An oracle bound:** a latent-state-aware compliant policy shows how much
  headroom the world leaves, so uplift can't hide behind a weak baseline.

What this does NOT prove: absolute recovery rates for any real merchant.
The rupee figures are properties of the simulated portfolio.

## What broke, and how we got out

The engine originally dropped actions scheduled *into the currently
executing time slot* — the post-resume retry's pre-debit notification
silently vanished, and the independent auditor flagged the retries as
notification-less (R3). The policy's own checks all passed; only the
auditor caught it, because it re-derives compliance from the log instead
of trusting the agent. That is the argument for adversarial self-audit in
one incident. Fix: schedule-time clamping plus a drain-until-empty slot
loop (`simlab/engine.py`), and a planted-violation test that keeps the
auditor itself honest.
